**结论：先自用，不要当托管服务卖。** 拿 OpenWA 把你自己的外贸询盘号接进「AI 分拣 + 起草回复 + 写进表格」，第一周就能省时间。但是不要拿它去给客户托管 WhatsApp API，原因有三个。第一，WhatsApp 用户条款明确禁止「非个人用途」和「自动发消息」，OpenWA 自己的 README 也写了「不适合大规模商业消息」、「封号风险永远不为零」。第二，同类托管服务已经卖到 $4.5–6/会话/月（WasenderAPI），利润很薄。第三，客户的号被封了，售后要你来扛，这正是你不想做的定制和咨询活。如果想赚钱，可行的方向是卖「部署包 + n8n 工作流模板」这种一次性数字产品，不碰客户的账号和会话。

## 怎么做

先核对一下项目现状：仓库 2026-02-02 创建，2026-10-21 还有推送，16,009 星、3,740 fork，MIT 许可证（[GitHub API](https://api.github.com/repos/rmyndharis/OpenWA)）。它默认用 `whatsapp-web.js` 引擎，也能换成 `baileys`。每个会话的内存占用，前者约 300–500 MB，后者约 30–80 MB。它自带 Webhook（有 HMAC 签名）、仪表盘、按会话配代理、发送节流（`SEND_PACING_ENABLED`，默认关），还带一个 MCP 服务：默认 25 个只读工具，打开写权限后是 51 个（[README](https://github.com/rmyndharis/OpenWA)）。

**路线 A：自用的询盘助手（第 1–3 天）**

1. **准备号码**：用一张专门的外贸号，不要用主号。先用手机正常聊一两周养号（README 建议新号逐步升温）。
2. **租 VPS**：2 vCPU / 4 GB 内存（推断：价格在每月 5–10 美元）。选 `ENGINE_TYPE=baileys` 更省内存，一台机器能跑好几个号。
3. **部署**：用 `docker compose` 部署，仪表盘和 API 共用 2785 端口。端口只对内网或 Tailscale 开放，同时打开 CIDR 白名单和 API Key。README 提醒过：Docker socket proxy 不算安全边界，API 容器被攻破的话，等于拿到了主机 root 权限。
4. **扫码登录**：在仪表盘上扫码，把这个号作为「关联设备」登录。
5. **接 n8n**（同一台 VPS 自托管，或者用 OpenWA 的 n8n 社区节点）：
   - 流程是：收到消息的 Webhook → 过滤（只处理新联系人和询盘关键词）→ Claude API 做分类（询价 / 样品 / 售后 / 垃圾）并抽取字段（品名、数量、目的港、预算）→ 写进 Google Sheets 或 Notion → 把起草好的回复推到你的飞书。
6. **人工确认再发**：在飞书点「发送」后，n8n 再调用 OpenWA 的发送接口。**不做自动群发，也不主动给陌生号发第一条消息**，这样封号风险最低。

**路线 B：卖数字产品「外贸 WhatsApp 询盘自动分拣包」（第 4–7 天）**

- 产品内容包括：docker-compose 文件、n8n 工作流 JSON、Claude 分类提示词、Sheets 模板，再加一份 20 分钟的录屏教程。客户自己部署，号码和会话都在客户自己的 VPS 上。
- 在 Gumroad 或 Lemon Squeezy 上架，同时写一篇 SEO 长文：「WhatsApp 询盘自动整理到表格」。

| VPS 2C4G | 约 $6/月 × 3 个月 ≈ $18 | 推断价格 |
| 外贸小号 SIM | $5–10 | 推断 |
| Claude API（分类和草稿） | $10 | 推断：一天几十条询盘、用 Haiku 时用不完 |

## 用在哪些场景

1. **你自己的外贸询盘号**：阿里国际站、独立站和展会带来的询盘都进了 WhatsApp，消息分散，容易漏回。AI 分类、抽字段后写进表格，24 小时内必回的询盘推送提醒。
2. **独立站的 Click-to-WhatsApp 广告承接**：官方 API 下，客户从广告进来后有 72 小时免费窗口（[meetergo](https://help.meetergo.com/en/integrations/automation/whatsapp-pricing)）。量小的时候可以先用 OpenWA 验证话术和转化，量起来以后迁到官方 Cloud API。
3. **小型跨境卖家的售后**：查物流、退换货这类问答。AI 起草回复，人点一下就发。只回复客户发来的消息，不主动推送。
4. **给自己的 AI 代理一个 WhatsApp 的手和眼**：通过 MCP（默认只读的 25 个工具）让 Claude Code 每天早上总结「昨天谁问了什么、谁还没回」，写进日报。
5. **数字产品的买家**：东南亚、中东、拉美的小外贸公司和独立站卖家（推断：这些地区 WhatsApp 是主要商务沟通渠道），他们想要询盘整理，又不想每月付 SaaS 费。

## 能实现什么

- **自用（路线 A）**：询盘首次回复时间从「看到才回」变成「草稿 5 分钟内到手机」，漏回的询盘降到接近 0（推断）。每天分拣询盘的时间预计减少 30–60 分钟（推断：按每天 20–40 条询盘、每条手动分拣 1–2 分钟计算）。
- **数字产品（路线 B）**：定价 $29–49。3 个月内的目标是 SEO 长文每月 1,000–3,000 次访问，转化率按 0.5–1% 算，每月 5–30 单，收入 $150–1,500/月。**这些全是推断**，我没找到同类模板包公开的销量数据。
- **为什么这么定价**：同类托管 API 卖 $6/月起（[WasenderAPI](https://wasenderapi.com/pricing)），做 WhatsApp 机器人的外包公司一次性收 $1,000–3,500（[achiya-automation](https://achiya-automation.com/en/pricing)）。一次性 $29–49 的自部署包正好卡在中间，而且不需要你提供售后托管。

## 自动化架构

| 环节 | 谁来做 |
|---|---|
| 收消息、Webhook、会话保活 | OpenWA（Docker，VPS 常驻） |
| 过滤、路由、写表格、推飞书 | n8n 自托管（同一台 VPS） |
| 询盘分类、抽字段、起草多语言回复 | Claude API（Haiku 档），由 n8n 调用 |
| 每日询盘总结、跟进提醒 | VPS 上的 cron 每天跑一次，通过 OpenWA 的 MCP（只读）让 Claude Code 生成摘要推到飞书 |
| 监控 OpenWA 版本更新和会话掉线 | cron 每小时检查会话状态接口，掉线就推飞书；Renovate 或 Watchtower 提醒升级（**不自动升级**，WhatsApp Web 协议一变就可能出问题） |
| 写 SEO 文章、更新工作流文档 | Claude Code 起草，你来改 |
| **仍要人做** | 点「发送」确认；掉线后重新扫码；回复产品买家的邮件 |

稳定后每周大约 1.5–2.5 小时：扫码和检查 15 分钟，确认发送的时间算在原本的业务里，买家答疑 30–60 分钟，内容更新 30–60 分钟（推断）。

## 未来预测

- **6 个月**：OpenWA 热度还会持续。它 2026 年 2 月才创建，8 个多月就到了 1.6 万星，今天还在提交（[GitHub API](https://api.github.com/repos/rmyndharis/OpenWA)）。同类的 Evolution API 到 2026 年 7 月约 9.1k 星，增长平稳（[Star History](https://www.star-history.com/evolution-foundation/evolution-api)，数字取自搜索结果摘要，页面未打开）。这说明「自托管 WhatsApp 网关」是一个长期存在的需求，不是一阵风。
- **12 个月**：Meta 在一边收紧官方渠道，一边提价。2026-01-15 起，官方 Business API 禁止「以 AI 为核心产品」的通用聊天机器人，只允许客服、预约、销售等业务型 AI（[respond.io](https://respond.io/blog/whatsapp-general-purpose-chatbots-ban)）；2026-10-01 起服务消息超出部分收费。两件事都会把一部分小用户推向非官方网关。但 Meta 对非官方客户端的打击也可能升级。**这一点不确定**，我没找到 2026 年针对 whatsapp-web.js 或 Baileys 大规模封号的公开报道。
- **24 个月**：比较可能的走向是：非官方网关退成「验证期和低量场景」的工具，量起来的用户迁到官方 Cloud API。所以你的模板包最好同时支持 OpenWA 和官方 Cloud API 两种发送后端，Evolution API 已经这么做了。协议大改导致所有非官方库同时失效的可能性存在，概率我判断不了。

## 风险与对策

1. **平台条款和封号**：WhatsApp 用户条款禁止通过自动化方式访问服务、禁止群发和自动发消息、禁止未经授权的非个人用途（[WhatsApp Terms](https://www.whatsapp.com/legal/terms-of-service)）。
   - 对策：用专门的小号，只回复对方先发来的消息，人工确认后才发；打开 `SEND_PACING_ENABLED`；不用廉价机房 IP；业务量大了就迁到官方 Cloud API。
2. **卖产品的连带责任**：买家拿你的模板去群发，号被封了回来找你。
   - 对策：落地页和 README 写清楚「仅用于回复入站消息，不支持群发」；模板里不放群发节点；退款政策写明封号不退。
3. **安全**：仪表盘暴露在公网，或者 Docker socket 被利用，都可能导致整台主机被接管（README 明确提醒过）；会话文件被盗等于账号被盗。
   - 对策：端口只走 Tailscale；会话目录放在加密卷；API Key 按会话分开；不开 MCP 写权限。
4. **上游变化**：WhatsApp Web 协议更新会让引擎暂时失效；单人维护的项目也可能停更。
   - 对策：固定镜像版本，先在测试号上升级；模板设计成可以切换后端（OpenWA、WAHA、官方 Cloud API）。
5. **同类竞争**：WAHA 免费开源，还有 $5/月的社区档（[WAHA](https://waha.devlike.pro/)）；Evolution API 自带 Chatwoot、Typebot 集成。
   - 对策：不跟它们拼网关本身，只卖「外贸询盘分拣」这个具体场景的工作流和提示词。
